# AGENTS.md

How to work on Aura: what it is, how to add features, and how to ship them.
For deeper conventions see **CLAUDE.md**.

## What the app does

Aura turns a phone/webcam into an **automated visual monitor** — entirely in the browser with no backend. The user provides their own base URL + model from any OpenAI-compatible provider, with an API key if that provider needs one (a local server — Ollama, LM Studio, llama.cpp — does not).

- **Mission prompt** — what to watch for.
- **Action prompt** — what to announce when it happens.
- **Sensitivity** — confidence threshold (10–95%) for firing alerts.

Each scan cycle:
```text
frame → scanClient() → detection call → if triggered: action call → speak + vibrate + flash + webhook
```

## How to add a feature

### A) Tune model behavior (prompts / temperature)
Edit `lib/monitor.js`:
- Prompts: `buildDetectionPrompt()` / `buildActionPrompt()`.
- Temperatures: constants in `lib/aura.js` (`0.5`/`0.9`).
- Output parsing: `normalizeDetection` / `parseAction` in `lib/monitor.js`.

### B) Add a runtime control (slider / switch / text field)
1. Add the MD3 web component in `public/index.html` (give it an `id`).
2. Register it in the `els` map in `public/app.js`.
3. In `setupControls()`: restore from `localStorage`, wire event listeners, update state/UI.
4. Read `state.<yourSetting>` where the loop uses it.

### C) Add a new inference path
1. In `lib/aura.js`: add the call in `scanClient()` using the provider config pattern.
2. Wire it into `public/app.js`.
3. Add pure-function tests in `test/monitor.test.js` if parsers are involved.

```bash

```

## Deployment

Push to `main` → GitHub Actions builds and deploys `public/` to GitHub Pages.

Manual deploy:
```bash
npm run deploy
```
Then enable Pages in repo settings → Source: `gh-pages` branch.

### Browser-model hosting constraint

Hugging Face model downloads do not work from a `workers.dev` deployment of
Aura. Deploy browser-model builds to GitHub Pages (`github.io`) instead, where
the downloads work.

## Guardrails
- No backend code — everything must work as a static site.
- User's API key must never be sent anywhere except directly to their chosen provider.
- Camera points at people: only deploy where recording is allowed.
- `public/sw.js` is generated by the build from `scripts/sw-template.js` — it caches
  the app shell so the PWA runs offline against a local model, and must never
  intercept provider calls or webhooks (same-origin `GET` only).

## Real-device E2E testing (Android)

Use **[ARTEMIS](https://github.com/google/artemis)** (Google, Apache-2.0) to
remote-control a real Android phone for end-to-end tests. It's the better way:
it drives the actual device from natural-language steps (accessibility tree +
vision), mirrors the screen live, and records logs and a replay of each task.
Prefer it over hand-rolled `adb shell input` taps or ad-hoc remote-debugging
scripts. Keep `scripts/dev-gate-e2e.mjs` for the headless-Chromium gate check;
ARTEMIS is for the reference device (Pixel 10, Chrome) — camera permission,
BROWSER-engine model download, WebGPU, speech and vibration all need real
hardware.

Setup (needs Python 3.12+ and a phone with USB debugging on; `start.sh`
installs ADB, scrcpy and FFmpeg):

```bash
git clone https://github.com/google/artemis.git && cd artemis
./start.sh
uv run artemis mcp --install claude   # expose it to Claude Code as an MCP server
uv run artemis ui                     # optional: web console with live mirroring
```

Example run against a deployed build:

```bash
uv run artemis run "Open Chrome, go to the Aura GitHub Pages URL, allow the camera, \
  switch the engine to BROWSER, start monitoring and report the status line text" \
  --profile flash
```

`--profile flash` is the fast reactive loop (~3–5 s/step); use `pro` for
multi-step flows that need planning and verification. Don't paste API keys into
task prompts — ARTEMIS logs them; use a local provider or demo mode instead.
